# Model card: SentinelAI detectors

## Intended use

SentinelAI flags minutes of service telemetry that look unusual for the time of day and week. Each flag comes with an explanation, so an engineer can decide quickly whether it's worth investigating.

**Not intended for:** declaring security incidents, blocking traffic, or any automated action. An anomaly score measures how unusual something is, not whether it is harmful.

## Data

- **Source:** synthetic telemetry generated by `sentinel/data.py` for a fictional service, *orders-api*. It is one-minute resolution over 14 days, with 7 raw metrics: requests per second, CPU %, memory %, p95 latency, error rate, outbound data and failed sign-ins.
- **Structure:** a daily load cycle, lighter weekends, correlated metrics (CPU and latency follow load), and noise.
- **Labels:** 8 types of injected anomaly episode. Each type is described in `ANOMALY_DESCRIPTIONS` and shown in the dashboard.
- **Split:**
  - **Training:** days 1 to 7. This includes two anomaly episodes (0.67% of minutes), because real training data is never perfectly clean.
  - **Test:** days 8 to 14, with 13 episodes covering every type.
  - **Validation:** a separate dataset generated with seed 1000, used only to tune hyperparameters.

## Features

Every feature is a **robust z-score**: (value − median) / scale, computed for each hour of the day and kept separately for weekdays and weekends. The scale is the larger of 1.4826 × MAD and IQR / 1.349. Two ratio features (outbound data per request, CPU per request) capture relationships between metrics. Because z-scores read as "typical deviations from normal for this time", the explanations can use them directly.

## Detectors

| | Robust baseline | Isolation Forest |
|---|---|---|
| Score | Largest absolute z-score across the 9 features | Isolation Forest anomaly score on the absolute z-scores (clipped at 12) |
| Settings | None | 400 trees, 4,096 samples per tree, chosen on the validation dataset (`python -m sentinel tuning`) |
| Threshold | Q3 + 3 × IQR of training scores | Same rule |
| Explanation | Each feature's share of the total absolute z-score | Occlusion: reset each feature to typical (z = 0) and measure how much the score drops |
| Strength | Transparent, fast, and good for single-metric extremes | Can, in principle, catch unusual combinations |
| Weakness | Judges each feature on its own | More false alerts here, and a score with no natural unit |

**Why a quartile fence, not a percentile?** The training data contains a little contamination. With 0.67% anomalous minutes, a 99.5th-percentile threshold lands *inside* the anomaly scores. Quartiles barely move when a small share of points are extreme. `tests/test_detectors.py` demonstrates this.

## Results (test week, seed 42)

| Metric | Robust baseline | Isolation Forest |
|---|---|---|
| Precision (per minute) | 0.963 | 0.711 |
| Recall (per minute) | 0.928 | 0.905 |
| F1 | 0.945 | 0.796 |
| Average precision | 0.975 | 0.866 |
| Episodes detected | 13 of 13 | 13 of 13 |
| False alerts per day | 2.0 | 17.6 |

On 4 other random datasets, baseline F1 ranged from 0.90 to 0.95 and Isolation Forest from 0.74 to 0.83. The full report is in [`reports/evaluation.md`](../reports/evaluation.md). CI regenerates it on every push and fails if the results change.

**Interpretation.** On this data, the simple baseline beats Isolation Forest. That's an honest result, not a failure of the experiment: most injected anomalies push one metric far from normal, which is exactly what the baseline measures. Isolation Forest raises many more one-minute false alerts. Isolation-based methods would be expected to earn their complexity on anomalies defined by unusual *combinations*, and the `subtle_multi_metric` type is a first, small step in that direction.

## Caveats

- **Synthetic data.** These numbers say nothing reliable about real telemetry, which has drift, deployments, missing data and anomaly shapes that nobody planned for.
- **Optimism.** The threshold rule was changed during development, while test results were visible. The hyperparameters were tuned on separate validation data, but the threshold rule's selection wasn't fully blind.
- **No drift handling.** The profiles are fitted once. Real use needs regular retraining, and a way to stop anomalies leaking into the baseline.
- **Explanations describe the model, not causes.** "CPU was 5.7 typical deviations high" says why the detector flagged a minute. It doesn't say why the CPU was high.
- **Ground truth is shown in the dashboard only because the data is synthetic.** In real operations, every alert would need investigation to classify.
